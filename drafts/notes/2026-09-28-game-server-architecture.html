00

밑단: TCP vs UDP — 무엇을 보장하고 무엇을 포기하나

transport
정의

둘 다 IP 위에서 "바이트를 상대 프로세스까지 나르는" 전송 계층 프로토콜. TCP는 연결·순서·전달을 보장하는 스트림이고, UDP는 아무것도 보장하지 않는 개별 데이터그램(패킷) 발사다.

어떻게
  • TCP: 3-way handshake로 연결을 만들고, 모든 세그먼트에 시퀀스 번호를 붙여 수신 측이 순서를 재조립한다. 유실되면 재전송하고, 재전송이 도착할 때까지 그 뒤에 이미 도착한 데이터도 앱에 안 넘겨준다(head-of-line blocking). 혼잡 제어가 전송 속도도 조절한다.
  • UDP: 핸드셰이크 없음. 헤더 8바이트(출발/도착 포트, 길이, 체크섬)를 붙여 그냥 쏜다. 유실·중복·순서 뒤바뀜이 전부 가능하고, 처리 여부는 전적으로 애플리케이션 몫.
트레이드오프 — 왜 실시간 게임이 UDP를 고르나

게임의 위치·상태 패킷은 수명이 한 tick이다. 유실된 50ms 전 위치를 재전송받아봤자 이미 다음 tick 데이터가 와 있다. 그런데 TCP는 그 죽은 데이터를 살리겠다고 이후의 신선한 데이터까지 막는다(HOL blocking) — 랙 스파이크의 주범. UDP는 잃어버린 건 버리고 최신 것만 쓰면 되니 레이턴시가 일정하다. 대신 "이 메시지는 꼭 도착해야 함"(아이템 획득 등)이 필요하므로, 실전은 UDP 위에 신뢰 채널/비신뢰 채널을 모두 갖춘 자체 프로토콜을 얹는 형태가 표준이다(QUIC이 같은 동기로 UDP 위에 지어진 것과 동일한 이유).

한 줄 — TCP의 "전부 순서대로 전달" 보장은 곧 "오래된 데이터가 새 데이터를 막을 수 있다"는 뜻이고, 실시간성엔 그게 독이다.

01

프로토콜 계층 — REST와 UDP는 같은 층이 아니다

layering
흔한 오해 — "REST API로 할까, UDP로 할까"는 같은 층위의 선택지다? 아니다. REST는 HTTP 위의 설계 스타일이고, HTTP는 TCP 위의 애플리케이션 프로토콜이며, TCP/UDP는 그 밑의 전송 계층이다. REST API도 결국 밑에서는 TCP로 나르고 있다.

어떻게

실제 선택지는 이것이다: "HTTP(+REST)라는 기성 중간층을 쓸 것인가, 전송 계층 바로 위에 내 프로토콜을 직접 얹을 것인가." HTTP는 요청-응답 왕복 구조와 텍스트 헤더 오버헤드를 갖고 있어, 초당 수십 번 양방향으로 쏘는 용도에 안 맞는다. 그래서 게임은 그 층을 걷어내고 바이너리 직렬화(protobuf, FlatBuffers 등) + 자체 프레이밍으로 대체한다.

한 줄 — "REST vs UDP"가 아니라 "HTTP 중간층을 쓸 거냐, 걷어낼 거냐"의 선택이다.

02

요청-응답 서버 vs 시뮬레이션 서버

architecture
정의

백엔드에는 성격이 다른 두 세계가 있다. 요청-응답 세계(전형적 앱/API 서버)는 stateless — 요청을 받아 처리하고 응답하면 끝, 상태는 전부 DB/캐시에 있다. 시뮬레이션 세계(실시간 게임 서버)는 stateful — 세션(매치)의 살아있는 상태를 서버 프로세스의 메모리에 들고, 요청이 없어도 스스로 돈다.

요청-응답 (앱 서버)시뮬레이션 (게임 서버)
상태stateless — DB/캐시가 진실stateful — 프로세스 메모리가 진실
구동 방식요청이 와야 일함 (수동)tick 루프가 상시 돎 (능동, push)
연결짧은 요청 단위지속 연결 (세션 내내)
라우팅아무 인스턴스나 처리 가능세션 어피니티 필수 — "이 매치는 반드시 저 프로세스"
스케일링수평 확장 쉬움어려움 — 상태를 든 채 옮길 수 없음
장애다른 인스턴스로 재시도하면 끝프로세스 죽으면 그 세션의 상태가 소멸
우선 지표정합성 · 처리량(RPS)레이턴시 · tick 안정성 · 동접(CCU)
왜

매 조작마다 상태를 DB에서 읽고 쓰면 tick 예산(수십 ms)을 절대 못 맞춘다. 상태를 메모리에 두는 순간 위 표의 오른쪽 열 전부 — 어피니티, 어려운 스케일링, 취약한 장애 복구 — 가 연쇄적으로 따라온다. 게임 서버 설계의 어려움 대부분이 이 stateful함의 대가다.

03

게임 루프와 tick rate

runtime
정의

tick은 서버가 월드 상태를 한 번 갱신하는 주기. tick rate는 초당 tick 수 — 대전 FPS는 60~128, MMO나 저속 장르는 10~30 수준.

어떻게
next = now()
loop:
    next += 50ms                 # 20 tick/s → tick당 예산 50ms
    inputs = drain(입력_큐)        # 그동안 도착한 클라이언트 명령 수집
    world.step(inputs, 50ms)     # 검증 → 물리·판정·AI 시뮬레이션
    for p in players:
        send(p, world.visible_to(p))  # 플레이어별 필터링 후 브로드캐스트
    sleep_until(next)            # 남은 시간 대기 — 초과하면 "tick 밀림"

핵심 제약: 시뮬레이션 + 직렬화 + 전송이 tick 예산 안에 끝나야 한다. 초과하면 다음 tick이 밀리고, 밀림이 누적되면 방 전체가 랙에 빠진다. 그래서 매치 하나는 보통 싱글 스레드 루프로 돌려 락을 아예 피하고(방 단위로 스레드/프로세스를 나눔), GC 멈춤이 tick을 밀 수 있어 GC 없는 언어(C++, Rust)를 쓰거나 GC 튜닝에 공을 들인다. 액터 모델(Orleans, Akka류)도 "방 = 액터"로 같은 격리를 얻는 인기 선택지. C++과 Rust는 성능은 같은 체급(둘 다 GC 없는 네이티브/LLVM — 같은 인스턴스에서 같은 급으로 돈다)이고, 선택을 가르는 건 생태계(엔진 데디케이티드 서버 통합은 C++ 쪽이 깊음)와 안전성(Rust는 데이터 레이스·메모리 버그를 컴파일 타임에 차단 — 죽으면 판이 날아가는 장수명 stateful 서버에 실질적 장점)이다.

트레이드오프

tick rate를 올리면 판정이 정밀해지고 체감 반응이 빨라지지만, CPU·대역폭 비용이 정비례로 늘고 방당 수용 인원이 준다. 장르가 요구하는 최소치를 찾는 게 용량 설계의 출발점.

한 줄 — 앱 서버는 요청이 없으면 놀지만, 게임 서버는 요청이 없어도 초당 N번 일한다. 그 N번의 마감시한이 전부다.

04

용량 산정 — RPS가 아니라 CCU

capacity
왜 단위가 다른가

앱 서버는 요청을 몇 ms 처리하고 자원을 반납하므로 용량 = 처리량(RPS, Requests Per Second). 실시간 서버는 접속자 1명당 상시 비용이 든다:

  • 메모리 ∝ 연결 수 — 소켓 버퍼 + 세션 상태가 접속 내내 상주
  • CPU ∝ 시뮬레이션 — 그 유저가 속한 방의 tick을 매 주기 돌려야 함
  • 대역폭 — N명 방에서 매 tick N명에게 상태를 보내므로, 상태 크기가 인원에 비례하면 방 트래픽은 N² 성격으로 커진다
어떻게 계산하나

단위를 CCU(동시 접속)와 방(매치)당 코어 예산으로 잡는다. "방 하나 = 코어 0.5개 + 메모리 X MB, 서버 한 대 = 방 M개" 식으로 산정하고, 방 수요에 따라 서버 수를 늘린다. 접속자 수 대비 하드웨어 사양이 앱 서버보다 훨씬 높아 보이는 이유가 이것 — 다만 비싼 건 실시간 매치 파트이고, 로그인·상점 같은 메타 파트는 일반 앱 서버와 같은 효율이다.

자릿수 감각 (ballpark — 게임마다 편차 큼)

연결 자체는 거의 공짜고 tick 시뮬레이션이 CPU를 다 먹으므로, 예산은 "플레이어당"이 아니라 "방당"으로 잡는다:

장르tick방당 CPU 예산
턴제·카드·보드이벤트 구동 (tick 없음)코어 1개 = 수천 방 — 사실상 앱 서버와 동급
캐주얼 실시간10~20Hz, 가벼운 물리코어 1개 = 수십~수백 방
FPS급60~128Hz, 무거운 판정10~16인 매치 하나 = 코어 0.5~1개
  • 메모리: 연결당 수십~수백 KB(소켓 버퍼 + 세션 상태; 지속연결 게이트웨이 실측 예 ~47KB/연결). 월드 상태가 큰 MMO는 플레이어당 MB급.
  • 대역폭: 캐주얼 1~5KB/s, 고tick FPS는 플레이어당 하향 20~50KB/s.
  • 소인원 방(2인 등): N이 작으면 팬아웃(N²)은 무의미해지고 남는 변수는 tick rate × 시뮬레이션 무게뿐 — 2인 턴제는 한 프로세스에 방 수천 개, 2인이라도 60Hz 물리(격투 등)면 방당 예산을 제대로 잡아야 한다.
함정 — 버스터블 인스턴스 — 1GB·2vCPU급 micro 인스턴스(burstable, t계열)로 얼마나 받나? 메모리로는 수천 연결도 이론상 가능하고, 턴제면 1,000+ CCU·캐주얼 실시간이면 수십~200 CCU·FPS면 매치 1~2개 감각. 하지만 진짜 문제는 버스터블이라는 것 자체다: tick 루프는 지속적 CPU 부하라 크레딧을 계속 태우고, 고갈되면 베이스라인(~10~20%)으로 스로틀 → tick 밀림 → 전 방 랙사. 상시 tick 도는 매치 서버는 고정 성능 인스턴스를 쓰고, micro급은 개발·시그널링·소규모 메타 용도에 쓴다.

05

Authoritative server — 입력을 보내고, 상태를 받는다

design
정의

게임의 진실(판정·상태)은 오직 서버가 결정하고, 클라이언트는 입력(명령)만 보낼 수 있는 설계. "나 이 유닛 샀어"가 아니라 "유닛 구매를 요청한다"이며, 골드가 충분한지·그 칸이 비었는지는 서버가 검증한다.

왜

클라이언트는 유저의 손 안에 있다 — 메모리를 조작하든 패킷을 위조하든 언젠가는 뚫린다. 클라이언트가 보내는 것을 "사실"로 믿는 순간 치트가 가능해진다. 그래서 클라이언트가 보내는 데이터의 의미를 사실(state)이 아니라 의도(input)로 제한하는 것이 치트 방지의 구조적 기반이다.

트레이드오프

모든 판정이 서버 왕복을 거치므로 유저는 자기 입력의 결과를 RTT만큼 늦게 본다. 이 지연을 숨기는 기법들이 다음 카드(06). 반대 선택지 — 클라이언트 판정 — 는 반응성은 완벽하지만 경쟁 게임에선 치트 때문에 선택지가 아니다.

06

레이턴시 은닉 3종 세트

netcode
문제

authoritative 서버(05)에서 입력 → 서버 판정 → 결과 수신까지 RTT가 걸린다. 100ms 지연 후 캐릭터가 움직이면 게임이 안 된다. 세 가지 기법이 층층이 이를 숨긴다:

어떻게
  1. Client-side prediction — 클라이언트가 자기 입력의 결과를 서버 확인 전에 미리 시뮬레이션해서 보여준다. 내 캐릭터는 즉시 움직인다.
  2. Server reconciliation — 서버의 authoritative 결과가 도착하면 예측과 비교한다. 어긋났으면(서버가 "그 이동 무효" 판정) 클라이언트가 서버 상태로 되감고, 그 이후 보낸 입력들을 재적용한다. 어긋남이 크면 순간이동처럼 보이는 "고무줄(rubber-banding)" 현상이 이것.
  3. Lag compensation — 사격 판정 시 서버가 "쏜 시점에 쏜 사람이 봤던 과거 월드"로 상태를 되감아 명중을 판정한다. 서버는 최근 수백 ms의 상태 스냅샷을 링버퍼로 보관한다. 덕분에 핑이 있어도 조준한 대로 맞지만, 맞은 쪽 입장에선 "벽 뒤로 숨었는데 맞았다"가 생긴다 — 쏜 사람의 과거와 맞은 사람의 현재가 다르기 때문.
한 줄 — 예측으로 내 지연을 숨기고, 되감기로 예측 오차를 수습하고, 랙 보상으로 상대와의 시차를 심판이 흡수한다.

07

정보 필터링 (interest management)

design
정의

서버가 브로드캐스트할 때 각 플레이어에게 그 플레이어가 알아도 되는 정보만 골라 보내는 것. "전체 상태를 보내고 클라이언트가 가릴 부분을 정한다"가 아니라, 애초에 안 보낸다.

왜 — 두 가지 이유
  • 보안: 클라이언트에 도착한 데이터는 메모리를 뒤지면 볼 수 있다. 벽 뒤 적 위치를 보내면 월핵이, 상대의 비공개 자원(손패, 벤치, 골드)을 보내면 정보 치트가 가능해진다. 05와 같은 원리 — 클라이언트는 신뢰 경계 밖이다.
  • 대역폭: 대규모 월드에서 전원에게 전체 상태를 보내면 04의 N² 트래픽이 폭발한다. 관심 영역(시야, 근접 구역)만 보내 팬아웃을 자른다.
어떻게

tick 루프의 전송 단계가 world.visible_to(p) — 플레이어별 가시성 규칙(시야 판정, 공개/비공개 필드 구분, 구역 격자)을 통과한 부분집합만 직렬화한다. 판 종료 후 전체 정보 공개(리플레이, 결과 화면)는 그때 별도로 내려준다.

매치 상태의 생애주기 — 메모리가 진실이다

state
흔한 오해 — 게임 중의 상태(보드, 골드, HP)도 조작할 때마다 DB에 저장된다? 아니다. 매치 진행 중의 유일한 진실은 매치 서버 프로세스의 메모리이고, DB에는 판이 끝날 때 결과만 쓴다.
어떻게 — 오토배틀러류를 예로
  • 입력은 드문 명령: "유닛 구매", "3번 칸 배치", "리롤" 같은 이벤트. 좌표를 매 프레임 쏘는 FPS와 달리 입력 빈도가 낮다.
  • 서버가 검증 → 메모리 갱신 → 필터링 브로드캐스트(05·07). 전투 연출은 서버가 시뮬레이션한 결과(또는 결정적 시드)를 클라이언트가 재생.
  • 재접속: 클라이언트가 튕겼다 돌아오면 서버 메모리의 현재 상태를 스냅샷으로 통째로 내려줘 복원한다. 재접속 시 몇 초 로딩이 이 스냅샷 전송.
  • 영구 저장은 매치 종료 시 한 번: 최종 결과(등수, 레이팅 변동, 통계)만 메타 서버로 server-to-server 전달(직접 호출 또는 메시지 큐) → DB 커밋.
  • 서버 프로세스가 죽으면? 대부분의 게임은 그 판을 포기한다. 그래서 매치 서버의 안정성에 사활을 건다. (판 개념이 없는 MMO만 주기적 스냅샷 + 중요 이벤트 즉시 저장을 섞는다 — 거래·아이템 획득은 즉시, 위치는 주기적.)
한 줄 — 판 도중엔 메모리가 진실, 재접속은 스냅샷으로, DB는 종료 시 결과만. "언제 저장되나"의 답은 대부분 매치 종료 시점 한 번이다.

백엔드 토폴로지 — 두 세계와 한 판의 흐름

topology
구성

게임 백엔드는 "서버 두 개"라기보다 성격이 다른 두 세계로 나뉘고, 각 세계 안에서 서비스로 더 쪼개진다:

  • 메타(플랫폼) 서버 — 로그인·인벤토리·상점·전적·랭킹. 평범한 stateless HTTP 서버 + RDB/캐시. 결제·아이템 지급은 오히려 정합성이 최우선이라 트랜잭션 설계가 핵심.
  • 매치메이킹 — 큐를 관리하고, 조건이 맞으면 fleet에서 매치 서버를 배정.
  • 매치 서버 fleet — 판 하나를 시뮬레이션하는 stateful 프로세스들(02~08의 주인공).
  • 지속연결 게이트웨이 — 채팅·친구 프레즌스·파티·초대처럼 "실시간 push는 필요하지만 tick 시뮬레이션은 아닌" 것들. WebSocket 등 지속 연결로 처리한다. → 상세는 「실시간 WebSocket 게이트웨이」 노트 참고.
한 판의 흐름

① 로비·상점은 HTTP로 메타 서버와. ② 큐를 돌리면 매치메이킹이 매치 서버를 배정하고 클라이언트에 "저 주소로 접속, 이 토큰 지참"을 알린다. ③ 게임 중엔 메타 서버를 거치지 않고 매치 서버에 직접 연결한다 — 레이턴시 경로에 아무것도 안 끼운다. ④ 판이 끝나면 매치 서버가 결과를 메타 쪽에 server-to-server로 보고(중간에 메시지 큐를 끼우기도)하고, 클라이언트는 다시 로비(①)로.

왜 나누나

두 세계는 스케일 단위(RPS vs CCU), 배포 방식(10), 언어·런타임 선택까지 전부 달라서 한 덩어리로 만들면 양쪽 다 손해다. 관측 포인트: 게임사 백엔드 인력의 다수는 사실 메타 서버 — 즉 일반 API 서버 — 를 만든다.

10

배포와 스케일링 — 드레이닝과 fleet 오케스트레이션

ops
문제

stateless 서버는 롤링 배포로 아무 때나 인스턴스를 갈아끼우면 된다. 매치 서버는 진행 중인 판을 죽일 수 없다 — 인스턴스 교체가 곧 유저 수백 명의 판 파괴다.

어떻게
  • 드레이닝(draining): 구버전 서버를 "신규 매치 배정 금지"로 표시하고, 진행 중인 판이 자연히 끝날 때까지 기다린 뒤 회수한다. 배포가 몇 십 분~몇 시간 걸리는 이유.
  • fleet 오케스트레이션: 매치 서버 프로세스를 필요할 때 띄우고(또는 웜 풀에서 배정) 판이 끝나면 회수하는 전용 레이어. Kubernetes 위의 Agones, 클라우드 관리형 GameLift류가 이 역할 — 일반 오케스트레이터의 "아무 파드나 죽여도 됨" 가정이 안 통해서 전용 도구가 존재한다.
  • 리전 배치: 레이턴시는 물리 거리를 못 이기므로 매치 서버는 유저 가까운 리전에 분산 배치하고, 매치메이킹이 참가자들의 지연을 고려해 리전을 고른다.
한 줄 — stateless 세계의 배포 상식("아무 때나 갈아끼움")이 stateful 세계에선 성립하지 않는다. 세션의 수명이 배포의 단위가 된다.

호스팅 모델 — 전용 서버 / 리슨 서버 / P2P·릴레이

hosting
흔한 오해 — 멀티 게임에서 핑이 튀면 항상 게임사 서버 문제다? 게임에 따라 서버가 게임사에 없다. "호스트" 방식 게임에선 플레이어 중 한 명의 PC가 서버 역할을 하며, 그 사람의 가정용 회선이 전원의 핑을 좌우한다.
각 모델의 성격
  • 전용 서버(dedicated) — 게임사가 데이터센터에 운영. 전원에게 공평한 레이턴시, 치트 방어(05), 안정성. 대가는 fleet 운영비(10). 경쟁 게임의 표준.
  • 리슨 서버(listen server) — 플레이어 한 명의 기기가 서버 겸 플레이어. 운영비 0이지만: 전원 트래픽이 호스트의 가정용 회선(특히 좁은 업로드)을 거쳐 호스트 상황에 따라 전원 핑이 튀고, 호스트 본인은 핑 0ms라 판정에서 유리하며(host advantage), 호스트 이탈 시 호스트 마이그레이션(다른 플레이어를 새 호스트로 승격 — 그 몇 초간 전원 멈춤)이 필요하고, 호스트가 곧 심판이라 치트에 취약하다.
  • P2P + 릴레이 — 트래픽만 게임사 릴레이 서버로 중계해 NAT 통과·IP 노출 문제를 풀되, 게임 판정 권한은 여전히 클라이언트(호스트)에 있다. 전용 서버보다 훨씬 싸고 리슨 서버보다 연결이 안정적인 절충안.
  • (별개 계열) 롤백 넷코드 — 1:1 격투 게임 등에서 서버 없이 양쪽이 같은 결정적(deterministic) 시뮬레이션을 돌리고 입력만 교환한다. 상대 입력이 늦게 오면 예측으로 진행하다가, 도착하면 그 시점으로 되감아 재시뮬레이션(06의 reconciliation을 P2P에 적용한 꼴).
선택 기준

공정성과 치트 방어가 수익에 직결되면(경쟁·랭크) 전용 서버, 캐주얼·협동이라 비용이 우선이면 호스트/릴레이 계열로 기운다. "호스트 형이 유튜브 켜면 전원 핑이 튀는" 경험은 후자의 구조적 한계다.

WebRTC — P2P 연결의 표준 배관

transport
정의

브라우저·게임 엔진에 표준으로 들어 있는 P2P 연결 스택. 11번의 "P2P + 릴레이" 그림을 직접 구현할 때 쓰는 기성 부품으로, NAT 통과·암호화·데이터 채널까지 한 번에 준다. 게임 엔진용 공식/서드파티 패키지로 코드 몇 줄이면 데이터 채널이 열린다 — 단, 열리는 건 파이프까지다.

어떻게
  • 시그널링: 두 피어가 처음 만나려면 연결 정보(SDP, ICE candidate)를 교환할 작은 서버가 필요하다. 완전한 서버리스는 아니다 — 연결 성사 후엔 경로에서 빠진다.
  • NAT 통과 (ICE): STUN 서버로 자기 공인 주소를 알아내 직접 연결(hole punching)을 시도하고, 실패하면 TURN 릴레이 경유로 폴백한다. 11번의 "릴레이 서버"가 WebRTC에선 TURN이라는 표준 부품이다.
  • 데이터 채널: UDP 기반(SCTP over DTLS, 암호화 기본)이고 채널마다 신뢰/순서 보장 여부를 설정할 수 있다 — 00번에서 말한 "UDP 위 신뢰/비신뢰 채널"을 직접 만들 필요 없이 기성품으로 주는 셈.
헷갈리기 쉬운 지점 — "WebRTC를 쓰면 호스트 문제가 해결된다"? 아니다. WebRTC는 연결(전송)만 해결한다. 누가 판정 권한을 갖느냐는 그 위의 설계 선택이고, 한 피어를 authority로 세우면 리슨 서버 모델(host advantage·이탈·치트)이, 1:1 결정적 시뮬레이션이면 롤백 넷코드가 — 11번의 트레이드오프가 그대로 적용된다.

P2P의 실제 비용 — 왜 생각만큼 안 줄어드나

tradeoff
문제

"서버가 없으니 비용이 확 줄겠다"는 직관은 절반만 맞다. 문제의 뿌리는 네트워크 불안정이 아니라 신뢰할 수 있는 제3자가 없다는 것 자체다 — 판정, 정보 은닉, 결과 보고, 분쟁 중재가 전부 신뢰 주체를 필요로 하는 일이기 때문.

돈으로 해결 안 되는 것들
  • 치트 — 결정타. 심판이 없다. authoritative 검증(05)도 정보 필터링(07)도 사라진다: 호스트가 치트하면 끝이고, P2P에선 전체 상태가 모든 피어에 오가므로 맵핵이 공짜다. 판 결과를 서버에 보고하는 것도 클라이언트라 전적·랭킹·보상 조작이 가능하다. 랭크·경제·경쟁 요소가 있는 순간 P2P가 선택지에서 빠지는 이유.
  • desync. 단일 진실(서버 메모리)이 없어 피어 간 상태가 어긋나는 게 고질병. 롤백/락스텝은 모든 기기의 시뮬레이션이 비트 단위로 같아야 하는데(결정성), 플랫폼별 부동소수점 차이 하나로도 판이 갈라지고, 어긋났을 때 "누가 맞는지" 정할 기준도 없다.
  • 운영 관측 불가. 서버 로그가 없어 버그 재현·분쟁 처리·리플레이·치트 신고 검증이 어렵다. 직접 P2P는 상대에게 IP가 노출돼 저격 DoS·신상 문제로 이어질 수 있고, 이것 때문에 릴레이를 강제하면 아래 비용으로 되돌아온다.
비용이 생각만큼 안 줄어드는 이유
  • 시그널링 서버는 어차피 필요하고, 로그인·매치메이킹·전적 같은 메타 서버(09)도 그대로 필요하다.
  • TURN 릴레이 비용 회귀: NAT 통과는 꽤 실패한다(대칭형 NAT, 회사/학교망 등). 그 유저들은 릴레이 경유인데 TURN은 게임 트래픽 전체를 중계하므로, 릴레이 비율이 높으면 전용 서버 대비 절감폭이 크게 준다.
  • 스케일 한계: 풀메시 P2P는 연결 N², 각자 업로드 N-1배 — 가정용 업로드 대역폭 때문에 실질 4~8인이 한계. 인원이 늘면 결국 한 명을 호스트로 세우고(스타 토폴로지) 11번의 호스트 종속 문제로 회귀한다.
선택 기준

협동·캐주얼·친구끼리 방(치트 동기 없음, 결과가 안 중요) → P2P 절감 합리적. 랭킹·경제·경쟁이 있다 → 전용 서버 비용은 아끼는 대상이 아니라 제품의 일부다.

한 줄 — P2P가 지우는 건 서버 비용이 아니라 신뢰 주체다. 게임에 신뢰가 필요 없으면 싸고, 필요하면 어떤 형태로든 그 비용이 되돌아온다.

대량 유닛 동기화 — 몹 100마리가 전부 이벤트로 가나?

netcode
출발 질문 — 디펜스 게임에서 타워가 공격할 때마다 몹 100마리의 HP가, 몹과 영웅이 움직일 때마다 그 위치가 전부 이벤트로 네트워크를 타나? 어느 방식이든 "유닛별 개별 이벤트"로는 가지 않는다. 접근이 두 갈래로 갈린다.
접근 ① 상태 복제 (state replication) — "결과를 보낸다"

서버가 매 tick 유닛 상태를 내려주되, 유닛별 이벤트 100개가 아니라 tick당 패킷 1개에 변경분을 묶는다:

# 매 tick(예: 50ms) 서버 → 클라이언트, 패킷 1개:
[tick #1042 | 몹#3: x,y | 몹#17: hp-12 | 몹#54: x,y | 영웅#1: x,y]
  → 델타 압축: 지난 tick 대비 변한 유닛만, 변한 필드만 (안 움직인 몹 80마리 = 0바이트)
  → HP는 매 tick이 아니라 변할 때만
  → 양자화: 좌표를 필요 정밀도만큼만 (float 32bit → 16bit 격자 등)
  → 관심 영역(07): 시야 밖 유닛은 아예 제외

그래도 트래픽이 유닛 수에 비례하므로, 수백 마리가 상시 움직이는 장르에선 부담이 커진다.

접근 ② 결정적 락스텝 (deterministic lockstep) — "입력만 보낸다"

발상의 전환: 몹의 위치·HP는 전송할 데이터가 아니라 계산 결과다. 몹의 이동은 경로 탐색 AI가, 타워의 공격은 사거리·쿨다운 규칙이 결정하므로 게임 규칙에서 전부 유도된다. 그래서 모든 참가자가 같은 시뮬레이션을 각자 돌리고, 네트워크로는 플레이어 입력만 보낸다("3번 자리 타워 건설", "영웅 이동 명령"). 몹이 100마리든 1,000마리든 트래픽은 동일 — 고전 RTS가 저속 모뎀으로 유닛 수백을 돌린 방법이고, RTS 리플레이 파일이 수십 KB인 이유다(입력 로그가 전부). 메커니즘은 15번.

영웅 이동은 어느 쪽에서도 "이벤트"가 아니다

클릭(이동 명령)이 이벤트이고, 그 후 매 프레임의 위치는 시뮬레이션이 만든다. 락스텝이면 위치는 아예 전송되지 않고, 상태 복제라도 명령은 한 번 올라가고 위치는 서버 tick 패킷에 실려 내려온다.

결정적 락스텝 — 적군을 전송하지 않고 공유하는 법

netcode
원리

멀티인데 적군 데이터가 안 오가는 게 가능한 이유: 적군의 모든 행동은 초기 상태 + 게임 규칙 + 랜덤 시드 + 플레이어 입력들의 순수 함수다. 입력만 같은 순서로 맞춰주면 나머지는 수학처럼 모든 기기에서 똑같이 풀려나온다. 적군은 "공유"되는 게 아니라 각자에게서 동일하게 "재현"된다.

어떻게
  1. 같은 출발점: 같은 맵·웨이브 테이블·랜덤 시드로 시작. "웨이브 3은 tick 6000에 스폰"은 규칙이고, 랜덤 요소도 시드 공유 RNG라 같은 난수가 나온다.
  2. 입력 지연 스케줄링: 내 입력조차 즉시 적용하지 않는다. tick 100에 클릭하면 "tick 103에 P1이 건설"로 예약해 전원에게 전송하고, tick 103에 나를 포함한 전원이 동시에 적용한다. 그 사이가 상대에게 입력이 도착할 시간 — RTS에서 클릭하면 유닛이 미세하게 늦게 반응하는 것의 정체.
  3. lock: 각 클라이언트는 tick N에 대한 모든 플레이어의 입력(없으면 "입력 없음" 표시라도)이 도착할 때까지 tick N을 진행하지 못한다. 한 명이 랙 걸리면 전원이 잠긴다 — "플레이어를 기다리는 중..."의 정체.
  4. desync 감지: 주기적으로 각자 게임 상태의 해시(체크섬)를 교환해 다르면 desync 선언(중단 or 재동기화).
트레이드오프
  • 맵핵에 구조적으로 취약: 시뮬레이션을 돌리려면 전장의 안개 속 적 포함 전체 상태가 내 메모리에 있어야 한다. 07의 "애초에 안 보낸다" 방어가 불가능 — RTS 장르에 맵핵이 유독 많았던 이유.
  • 늦은 참가·재접속 곤란: 중간 참가자는 상태를 재현할 수 없어 입력 로그를 처음부터 빨리감기 재생하거나 상태를 통째로 덤프받아야 한다.
  • 결정성 유지 부담: 플랫폼 간 부동소수점 차이 하나로 desync(13) — 고정소수점 연산이나 플랫폼 통일로 방어한다.
  • 보너스: 리플레이가 공짜다 — 입력 로그가 곧 리플레이이고, 11의 롤백 넷코드는 락스텝의 lock(대기)을 예측+되감기로 대체한 사촌이다.
한 줄 — 같은 시드에서 출발해 같은 입력을 같은 tick에 적용하면, 몹 1,000마리도 1바이트 전송 없이 모든 화면에서 동일하다. 데이터를 받아서가 아니라 같은 계산을 하고 있어서 같은 것.
