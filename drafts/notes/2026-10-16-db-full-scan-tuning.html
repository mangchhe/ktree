풀스캔 세 곳 — DB CPU 튜닝 사례로 배우는 인덱스와 EXPLAIN

매일 저녁 DB CPU가 99%까지 차고 API 응답이 20배 느려졌다. 앱 서버는 한가했다. 원인은 인덱스를 못 타서 테이블을 통째로 읽는 쿼리 세 곳이었고, 캐시도 서버 증설도 없이 쿼리 수정과 인덱스로 풀었다 — API 평균 3.8배, DB load 5분의 1. 그 과정을 따라가며 DB 튜닝에 필요한 개념을 그림 위주로 정리했다.

00

상황 — 앱은 한가한데 DB만 바쁘다

symptom

DB는 vCPU 2개짜리 인스턴스. 첫 반응은 "DB를 키우자" 또는 "캐시를 붙이자"였다. 그 전에 DB가 무엇 때문에 바쁜지부터 봤다.

한 줄 — 앱이 한가하고 DB만 바쁘면, 서버를 늘리기 전에 DB가 어떤 쿼리에 시간을 쓰는지부터 본다.
01

풀스캔과 인덱스

basics

인덱스가 없는 컬럼으로 찾으면 DB에게는 왼쪽밖에 선택지가 없다. 이번 사례의 세 곳이 모두 이 경우였다.

한 줄 — 풀스캔은 책을 첫 장부터 넘기는 것, 인덱스는 책 뒤의 색인을 보는 것.
02

비용 = 1회 비용 × 횟수

priority
한 줄 — 튜닝 대상은 "느린 쿼리"가 아니라 "1회 비용 × 호출 수가 큰 쿼리"다.
03

DB load — CPU 몇 개에 몇 명이 몰렸나

metrics

클라우드 DB 모니터링(AWS Performance Insights)은 load를 쿼리별, 무엇을 기다렸나(wait event)별로 쪼개 보여준다. 이번엔 load의 96%가 executing이었다. 락이나 디스크가 아니라 CPU로 행을 읽고 비교하는 일 자체가 많다는 뜻이다.

한 줄 — load를 vCPU 수와 비교하고, executing이 대부분이면 "쿼리가 너무 많이 읽는다"를 의심한다.
04

모니터링 함정 — 리터럴 SQL에 개인정보가 찍힌다

gotcha

DB 모니터링은 같은 쿼리를 두 방식으로 묶는다. 값을 ?로 바꾼 정규화(쿼리 모양별 합산)와, 값까지 그대로인 리터럴(값마다 따로)이다. 전체 SQL을 보려고 리터럴 쪽을 열었더니 회원 식별키가 그대로 찍혀 나왔다. 분석은 정규화 쪽으로 충분하고, 정규화가 더 정확하다(같은 쿼리가 한 줄로 합쳐진다).

한 줄 — 쿼리 분석은 정규화 SQL로. 리터럴 SQL은 개인정보가 섞이니 출력·공유·스크린샷하지 않는다.
05

EXPLAIN 한 줄 읽기

explain

EXPLAIN SELECT …는 쿼리를 실행하지 않고 실행 계획만 보여준다. 한 줄이 "테이블 하나를 어떻게 읽나"다.

EXPLAIN ANALYZE는 실제로 실행해 시간을 재지만 그만큼 부하를 준다. 운영 DB에서 풀스캔 쿼리는 계획(EXPLAIN)만 봤다.

한 줄 — type 열에서 ALL을 먼저 찾고, 그 줄의 rows가 앞 단계 행마다 반복되는지 본다.
06

사례 A — 인덱스 없는 상관 서브쿼리

case

저녁 6시 푸시 배치가 "회원별 최신 한도 1건"을 상관 서브쿼리로 구했다. 상관 서브쿼리는 바깥 행마다 다시 실행된다.

SELECT member_id FROM quota_snapshot q
WHERE member_id IN (:4,500명) AND remaining <= 40
  AND created_at = (SELECT MAX(created_at) FROM quota_snapshot q2
                    WHERE q2.member_id = q.member_id)   -- 바깥 행마다 실행

예전에 "그룹별 최신 1건은 상관 서브쿼리가 안전하다"고 정리한 적이 있었다. 그 말은 상관 컬럼에 인덱스가 있을 때만 맞다. 이 테이블은 PK 외 인덱스가 없었다. 게다가 반년 전부터 아무도 쓰지 않는 테이블이어서, 인덱스를 다는 대신 이 필터를 지웠다.

한 줄 — 상관 서브쿼리가 안전한지는 "매번 실행되는 안쪽이 인덱스를 타나"로 판단한다.
07

사례 B — GROUP BY가 세미조인을 막는다

case

포인트 잔액 = 지갑별 최신 이력의 잔여량 합. 최신 이력을 이렇게 구했다.

SELECT h.* FROM point_history h
WHERE (h.wallet_id, h.created_at) IN (
    SELECT wallet_id, MAX(created_at) FROM point_history
    WHERE wallet_id IN (:내 지갑들) GROUP BY wallet_id)

MySQL은 IN (서브쿼리)를 보통 세미조인으로 바꿔 서브쿼리 결과로 바깥을 인덱스 조회한다. 그런데 서브쿼리에 GROUP BY·집계가 있으면 이 변환을 못 한다. 결과는 회원이 가진 지갑 수와 무관하게 호출마다 이력 테이블 전체(38만 행) 읽기. 새벽에도 330ms, 저녁엔 3초.

고친 방법: 집계를 조인 안으로 옮겨 내 지갑으로 먼저 좁힌 뒤 MAX를 구하고, 행을 꺼내지 않고 바로 SUM.

전 — 쿼리 2번
① 내 지갑 목록 (인덱스, 3ms)
② (id, 시각) IN (GROUP BY …)
   → 바깥 ALL 377,467
③ 앱에서 합산
후 — 쿼리 1번
SELECT SUM(h.remaining)
FROM wallet w
JOIN (SELECT wallet_id, MAX(created_at) m
      FROM point_history JOIN wallet …
      WHERE member_id = ?      -- 먼저 좁힘
      GROUP BY wallet_id) x …
JOIN point_history h ON … = x.m
-- 모든 단계 ref / eq_ref
한 줄 — (a, b) IN (SELECT … GROUP BY …)는 바깥 테이블을 통째로 읽는다. 집계는 조인 안에서, 내 데이터로 좁힌 뒤에.
08

사례 C — 모든 요청에 붙은 조인

case

앞의 둘을 고친 뒤에도 사람이 적은 밤에 DB CPU가 30%대였다. load의 60%가 인증 필터였다. 로그인된 요청이면 API와 무관하게 매번 회원 정보를 테이블 7개와 조인해 읽는데, 그중 2개의 조인 컬럼에 인덱스가 없었다.

요청 1건당 약 4.6만 행(회원 식별키 조회 2.2만 + 디바이스 2.2만 + 설정 2천). 시간당 1.3만 요청이면 6억 행이다(02).

왜 인덱스가 없었나: InnoDB는 FK 제약을 걸면 그 컬럼에 인덱스를 자동으로 만든다. 이 테이블들은 FK 제약 없이 ORM의 조인 매핑만 있었다. ORM의 조인 선언은 인덱스를 만들지 않는다.

한 줄 — 모든 요청이 지나가는 길(인증·필터)의 쿼리는 EXPLAIN을 꼭 본다. FK 제약 없는 조인 컬럼은 인덱스가 없을 수 있다.
09

루프 안의 쿼리는 N배

case

알림 배치가 대상자 1명마다 "이 알림을 이미 보냈나"를 물었다. 쿼리 하나는 풀스캔 한 번이지만, 대상자가 N명이면 N번이다.

ORM 세계에서 흔히 말하는 N+1과 같은 구조다. 이번에는 인덱스(①)로 1회 비용을 줄였다. 호출 수 자체가 문제가 되는 규모면 ②로 묶는다.

한 줄 — 반복문 안의 쿼리는 1회 비용 × 반복 수다. 루프 안에서 풀스캔이 돌면 가장 먼저 의심한다.
10

복합 인덱스와 커버링 인덱스

index

"이 식별키로 앱 가입자가 있나?"는 identity_key, platform, PK만 필요하다. InnoDB 보조 인덱스에는 PK가 자동으로 붙어 있어서, (identity_key, platform) 하나로 인덱스만 읽고 끝난다. 앞 컬럼이 같으므로 로그인용 identity_key 단독 조회도 같은 인덱스를 탄다.

한 줄 — 복합 인덱스는 왼쪽부터 쓰인다. 자주 같이 쓰는 조건을 왼쪽부터 묶으면 조회 여러 개를 한 인덱스로 덮는다.
11

인덱스는 정렬도 대신한다

index

WHERE member_id = ? AND type = ? ORDER BY created_at DESC LIMIT 1 — "최신 1건"은 인덱스 유무에 따라 일의 양이 완전히 다르다.

인덱스는 값이 정렬된 채로 저장돼 있어서, 조건 컬럼 뒤에 정렬 컬럼을 붙이면 정렬을 따로 할 필요가 없다. EXPLAIN의 Using filesort가 사라지고 LIMIT 1이 진짜 1건만 읽게 된다.

한 줄 — WHERE 컬럼 다음에 ORDER BY 컬럼을 이어 붙인 인덱스는 "찾기"와 "정렬"을 같이 해준다.
12

컬럼 순서 — 같다(=) 먼저, 범위 나중

index

조건: member_id = ? 그리고 exposed_at이 하루 범위. 같은 두 컬럼이라도 인덱스 순서에 따라 읽는 양이 다르다.

인덱스는 왼쪽 컬럼부터 차례로 좁힌다. 범위 조건을 만나면 거기서 좁히기가 끝난다. 그래서 등호 조건 컬럼을 앞에, 범위 컬럼을 맨 뒤에 둔다. type IN (…) 같은 조건은 이미 몇 행으로 좁혀진 뒤라 인덱스에 안 넣고 거르기만 해도 충분했다.

한 줄 — 복합 인덱스 순서: 등호(=) 컬럼 → 정렬 컬럼 또는 범위 컬럼. 범위가 앞에 오면 뒤 컬럼은 놀게 된다.
13

인덱스 거는 법 — 온라인 DDL과 비용

operate

인덱스는 공짜가 아니다. 저장 공간을 쓰고, INSERT·UPDATE 때 인덱스도 고쳐야 해서 쓰기가 조금 느려진다. 그래서 자주 도는 쿼리의 WHERE·JOIN 컬럼에만 건다. 앞 컬럼이 같은 인덱스 두 개((a, b)와 (a, b, c))처럼 중복 인덱스는 비용만 있다.

한 줄 — 인덱스는 거의 잠금 없이 걸리고 바로 쓰인다. 대신 쓰기 비용이 있으니 많이 도는 조회에만.
14

고치기 전에 — 결과가 같은지 검증

verify

잔액은 돈이다. 쿼리를 바꾸면 빨라지는 것보다 값이 그대로인지가 먼저다. 세 겹으로 확인했다.

①의 핵심은 새 쿼리와 다른 방식으로 기대 값을 계산하는 것이다(MAX 조인 대신 ORDER BY … LIMIT 1). 같은 방식으로 두 번 계산하면 같이 틀려도 모른다. ③을 위해 배포 전 기준값을 먼저 기록해 둔다. 나중엔 "전"을 다시 잴 수 없다.

한 줄 — 기대 값은 다른 계산식으로, 경계 케이스는 진짜 DB에서, 효과는 미리 적어 둔 기준값과 비교.
