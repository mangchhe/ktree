00

셰이더는 유니티 기술인가? — 정의

definition
흔한 오해 — 셰이더는 유니티(또는 특정 엔진)의 기능이다? 아니다. 셰이더는 GPU 위에서 도는 작은 프로그램이고, 그래픽 API(DirectX·OpenGL·Vulkan·Metal·WebGL)가 정한 규격이다. 유니티·언리얼·Godot·브라우저(WebGL)는 모두 그 위에 셰이더를 쓰기 쉽게 감싸는 틀을 얹었을 뿐이다.
정의

화면에 무언가를 그릴 때 GPU가 "이 꼭짓점은 화면 어디로 가나", "이 픽셀은 무슨 색인가"를 계산하는데, 그 계산식을 사람이 직접 쓴 것이 셰이더다. 이름은 원래 명암(shade)을 계산하는 데서 왔지만 지금은 색·투명·변형·왜곡·녹임 등 픽셀에 대한 거의 모든 계산을 맡는다.

왜 신기해 보이나

보통 연출은 그림(스프라이트)을 갈아 끼워서 만든다. 셰이더는 그림은 그대로 두고 그림을 칠하는 방법을 바꾼다. 그래서 그림 한 장 없이도 "몸이 녹는다", "빛난다", "흑백이 된다" 같은 효과를 어떤 캐릭터에든 똑같이 입힐 수 있다.

한 줄 — 셰이더는 엔진 기능이 아니라 GPU 프로그램이다. 엔진은 그걸 쓰기 쉽게 해줄 뿐.

01

CPU와 GPU — 왜 따로 계산하나

hardware
정의

CPU는 소수의 강한 코어로 복잡하고 갈래 많은 일을 순서대로 빨리 한다. GPU는 수천 개의 약한 코어로 같은 계산을 수많은 데이터에 동시에 한다.

어떻게

1080p 화면은 약 200만 픽셀이고, 초당 60번 그리면 1억 2천만 번 "이 픽셀 색은?"을 물어야 한다. 픽셀끼리는 서로 상관이 없으므로(옆 픽셀 계산을 기다릴 필요가 없음) 같은 셰이더를 픽셀마다 따로 돌리면 된다. GPU는 바로 이 "같은 코드 × 엄청난 수의 데이터"에 맞춰 만들어졌다.

그래서 생기는 규칙
  • 셰이더 한 번은 자기 픽셀 하나만 안다. 옆 픽셀이 무슨 색인지 물어볼 수 없다(필요하면 텍스처를 한 번 더 읽는다).
  • 상태를 기억하지 못한다. "지난 프레임에 얼마나 녹았나"는 밖(CPU)에서 값으로 넣어줘야 한다 → 05.
  • 갈래(if)가 많으면 손해다 — 같은 묶음의 픽셀들이 다른 길로 가면 GPU는 두 길을 다 걷는다 → 12.
한 줄 — GPU는 "같은 계산을 픽셀마다 동시에" 하는 기계이고, 셰이더는 그 "같은 계산"이다.
↑ 목차
02

렌더링 파이프라인 — 꼭짓점에서 픽셀까지

pipeline
정의

CPU가 "이 그림을 여기 그려라"를 GPU에 넘기면(드로우콜), GPU는 정해진 단계를 순서대로 거쳐 화면 픽셀을 만든다. 이 중 두 단계를 사람이 프로그램할 수 있다 — 그게 정점 셰이더와 프래그먼트 셰이더다.

2D 스프라이트에서는

스프라이트 한 장은 보통 꼭짓점 4개짜리 사각형이다. 그래서 정점 셰이더는 4번 돌고, 프래그먼트 셰이더는 그 사각형이 덮는 수천 개 픽셀마다 돈다. 2D 연출의 거의 모든 재미는 프래그먼트 쪽에서 나온다.

한 줄 — 꼭짓점 → (정점 셰이더) → 픽셀 찾기 → (프래그먼트 셰이더) → 섞기. 괄호 둘이 셰이더다.
↑ 목차
03

정점 셰이더 vs 프래그먼트 셰이더

stages
정점 셰이더 (vertex)

꼭짓점 하나를 받아 화면의 어디에 놓일지를 계산한다. 위치를 흔들면 깃발이 펄럭이고, 부풀리면 외곽선용으로 커진다. 여기서 계산한 값(색·UV 등)은 다음 단계로 넘어가면서 꼭짓점 사이에서 자동으로 보간된다.

프래그먼트 셰이더 (fragment / pixel)

픽셀 하나를 받아 최종 색과 투명도를 돌려준다. 텍스처에서 색을 읽고, 곱하고, 섞고, 아예 그리지 않겠다고 버릴 수도 있다(clip/discard → 07). 녹임·빛남·흑백·외곽선 같은 2D 효과는 대부분 여기서 만든다.

// 아주 단순한 형태 (HLSL)
v2f vert(appdata v) {            // 꼭짓점마다
    v2f o;
    o.pos   = UnityObjectToClipPos(v.vertex);   // 화면 위치
    o.uv    = v.uv;                              // 텍스처 좌표는 그대로 넘김
    o.color = v.color;                           // 스프라이트 색(알파 포함)
    return o;
}
fixed4 frag(v2f i) : SV_Target { // 픽셀마다
    fixed4 c = tex2D(_MainTex, i.uv) * i.color; // 그림 색 × 틴트
    return c;
}
한 줄 — 정점 셰이더는 "어디에", 프래그먼트 셰이더는 "무슨 색으로".

04

언어와 엔진 — HLSL·GLSL·ShaderLab·Shader Graph

tooling
층위
  • 셰이더 언어 — HLSL(DirectX 계열), GLSL(OpenGL·WebGL), MSL(Metal). 문법은 C와 비슷하고 float4·lerp·saturate 같은 벡터·수학 함수가 기본이다.
  • 엔진의 껍데기 — 유니티의 ShaderLab은 "속성 목록·블렌딩 설정·패스"를 적는 틀이고, 그 안에 HLSL 코드를 넣는다. 유니티가 그 HLSL을 기기마다 다른 언어로 번역해 준다(PC는 DirectX, 아이폰은 Metal, 안드로이드는 OpenGL ES/Vulkan).
  • 노드 편집기 — Shader Graph(유니티)·Material Editor(언리얼)는 코드 대신 상자를 선으로 이어 같은 것을 만든다. 결과물은 결국 셰이더 코드다.
코드 vs 노드

노드는 결과를 바로 보며 만들 수 있어 실험에 좋다. 코드는 짧고, 비교·리뷰·버전 관리가 쉽고, 노드가 못 하는 세밀한 최적화가 된다. 작은 2D 효과 몇 개면 코드 한 파일이 더 다루기 쉽다.

한 줄 — 언어는 GPU 표준, ShaderLab/Shader Graph는 엔진이 얹은 편의 층, 기기별 번역은 엔진이 해준다.
↑ 목차
05

값을 넘기는 세 통로 — 정점 데이터·유니폼·텍스처

inputs
정의

셰이더는 기억이 없으므로(01) 필요한 값을 매번 밖에서 받아야 한다. 통로는 셋이다.

셋의 차이
  • 정점 데이터 — 꼭짓점마다 붙은 값: 위치·UV·색(RGBA). 스프라이트의 "색" 설정은 여기로 들어간다. 그림마다 다른 값을 줄 수 있다.
  • 유니폼(uniform) = 재질 속성 — 한 번 그리는 동안 모든 픽셀이 같은 값: "불씨 색", "노이즈 크기", "시간". 재질(Material)에 붙어 있다.
  • 텍스처 — 그림 자체. 픽셀마다 좌표(UV)로 읽는다. 무늬·마스크·노이즈 이미지도 텍스처로 줄 수 있다.
어느 통로를 쓰나 — 이게 성능을 가른다

"적마다 녹는 정도가 다르다" 같은 개체별 값을 재질 속성으로 넣으면, 개체마다 다른 재질 상태가 생긴다. 그러면 GPU에 "묶어서 한 번에 그려라"를 못 한다 → 06. 같은 값을 정점 색의 한 칸(예: 알파)에 실으면 재질은 하나로 남는다.

한 줄 — 모두 같은 값이면 재질 속성, 개체마다 다른 값이면 정점 데이터. 이 선택이 드로우콜 수를 정한다.
↑ 목차
06

드로우콜과 배칭 — 왜 "재질이 같아야" 묶이나

performance
정의

드로우콜은 CPU가 GPU에 "이 설정으로 이것을 그려라"를 한 번 지시하는 것이다. 그리는 일 자체보다 지시를 준비하는 비용이 크다 — 재질·텍스처·설정을 바꿔 끼우는 것이 비싸다. 모바일에서는 드로우콜 수가 프레임을 좌우하므로 보통 예산(예: 50 이하)을 정해둔다.

배칭

같은 재질·같은 텍스처를 쓰는 그림 여럿을 엔진이 하나로 합쳐 한 번에 그리는 것. 스프라이트를 아틀라스(큰 한 장)에 모으는 이유도 텍스처를 같게 만들어 묶이게 하려는 것이다. 단, 재질 값이 하나라도 다르면 묶이지 않는다(파이프라인마다 규칙은 조금씩 다르다 — URP의 SRP Batcher는 "같은 셰이더"면 준비 비용을 줄여준다).

실전 사례 — 적 24마리가 동시에 녹을 때

녹는 진행도를 재질 속성으로 주면 24마리가 24개의 다른 상태가 되어 드로우콜이 24개 는다(예산의 절반). 진행도를 스프라이트 색의 알파로 넘기고 셰이더가 "알파 = 1 − 진행도"로 읽게 하면, 재질은 하나로 남아 한 번에 그려진다. 대신 알파를 더 이상 "투명도"로 못 쓰지만, 녹는 효과에서는 어차피 투명도 대신 "갉아먹힘"이 사라짐을 표현하므로 잃는 게 없다.

한 줄 — 개체마다 다른 값은 재질에 넣지 말고 정점 데이터에 실어라. 그래야 묶인다.

07

투명과 블렌딩 — 알파·premultiplied·clip

transparency
정의

픽셀의 알파(A)는 불투명도다. 블렌딩은 프래그먼트 셰이더가 낸 색을 이미 화면에 있는 색과 섞는 고정 단계이고, 섞는 공식을 설정으로 고른다.

두 가지 투명 처리
  • 섞기(blend) — 반투명. 일반 공식은 결과 = 새색×α + 뒤색×(1−α). 2D 스프라이트는 흔히 premultiplied alpha를 쓴다: 색을 미리 α로 곱해두고 Blend One OneMinusSrcAlpha로 섞는다. 가장자리에 하얀/검은 테두리가 생기는 문제를 막아준다.
  • 버리기(clip / discard) — 이 픽셀은 아예 그리지 않는다. 반투명이 아니라 "있거나 없거나". clip(x)는 x가 0보다 작으면 픽셀을 버린다. 녹는 효과의 "갉아먹힌 구멍"이 이것이다.
트레이드오프

반투명은 뒤에 그려진 것을 다시 읽어 섞는 비용이 있고, 그리는 순서가 중요해진다(뒤부터 그려야 맞게 섞인다). 버리기는 순서 문제가 없지만 경계가 딱딱하다 — 그래서 녹는 경계에 빛나는 띠를 둘러 딱딱함을 감춘다(09).

한 줄 — 반투명은 "섞는다", clip은 "안 그린다". 녹는 효과는 clip으로 구멍을 내고 경계를 빛으로 덮는다.

08

노이즈 — 텍스처 없이 수학으로 무늬 만들기

procedural
정의

노이즈는 "무작위처럼 보이지만 같은 입력엔 늘 같은 값을 내는" 부드러운 얼룩 무늬다. 구름·불·연기·녹는 경계처럼 자연스러운 불규칙함이 필요할 때 쓴다.

어떻게 — 값 노이즈(value noise)
  1. 좌표를 격자로 나눈다(floor).
  2. 격자 꼭짓점마다 해시 함수로 0~1 난수를 만든다 — frac(sin(...)*큰수) 류의 계산. 같은 좌표엔 늘 같은 값.
  3. 칸 안의 점은 네 꼭짓점 값을 부드럽게 보간한다(smoothstep 곡선).
  4. 크기가 다른 노이즈 두세 겹을 더하면 굵은 덩어리 + 잔 부스러기가 섞인 자연스러운 얼룩이 된다.
텍스처 vs 수학

노이즈 이미지를 텍스처로 줘도 된다. 수학으로 만들면 읽을 파일이 없어 빌드에서 빠질 일도 없고, 해상도 걱정도 없다. 대신 계산 비용이 든다. 좌표를 무엇으로 잡느냐도 중요하다 — 텍스처 좌표(UV)는 그림이 아틀라스의 어디에 얼마 크기로 있느냐에 따라 범위가 달라져, 같은 그림이라도 결이 달라질 수 있다. 텍스처 픽셀 단위로 환산하면 그림 크기와 무관하게 결이 일정하다.

한 줄 — 노이즈 = 해시 난수 + 부드러운 보간. 자연스러운 불규칙함의 재료다.
↑ 목차
09

디졸브 해부 — 몸이 녹아 사라지는 효과

effect
정의

디졸브(dissolve)는 그림이 불규칙한 구멍들로 갉아먹히듯 사라지는 효과다. 많은 게임에서 유닛이 죽거나 순간이동할 때 쓴다. 핵심은 "흐려진다"가 아니라 "구멍이 퍼진다"는 점 — 그래서 반투명 페이드보다 훨씬 물질적으로 보인다.

fixed4 frag(v2f i) : SV_Target {
    fixed4 c = tex2D(_MainTex, i.uv);
    float p = 1 - i.color.a;               // 진행도는 정점 알파로 받는다 (06)
    float n = Noise(i.uv * 크기);           // 0~1 얼룩 (08)
    float d = n - p;
    clip(d);                               // n < p 이면 이 픽셀은 없다
    float edge = 1 - saturate(d / 띠두께);  // 경계에 가까울수록 1
    c.rgb = lerp(c.rgb, _EdgeColor.rgb, edge);
    return c;
}
세계관에 맞추기

레퍼런스(예: SF 게임의 유닛이 푸른 에너지로 흩어지는 연출)에서 가져올 것은 구조다 — "몸 자체가 풀린다". 경계 색과 재료는 우리 세계가 정한다. 적이 "재와 불씨가 뭉친 존재"라면 경계는 불씨색으로 타고, 그 위로 재가 피어오르는 그림을 얹는다. 셰이더(몸이 녹음)와 그림(재가 오름)이 두 겹으로 한 장면을 만든다.

한 줄 — 디졸브 = 노이즈 < 진행도면 버리고, 그 경계를 빛으로 칠한다. 진행도 하나로 0%에서 100%까지 녹인다.
↑ 목차
10

빌드 함정 — 에디터에선 되는데 폰에선 사라진다

build
무슨 일이 일어나나

엔진은 빌드 용량을 줄이려고 "쓰이지 않는 셰이더"를 빌드에서 뺀다(셰이더 스트리핑). 그런데 엔진이 "쓰인다"고 판단하는 근거는 재질이 그 셰이더를 가리키느냐다. 코드에서 이름으로만 찾는(Shader.Find("이름")) 셰이더는 엔진이 쓰임을 모른다 → 에디터에선 모든 셰이더가 있으니 잘 되고, 폰 빌드에선 null이 되어 조용히 빠진다.

확실히 넣는 법 (유니티)
  • 셰이더를 Resources 폴더에 두고 Resources.Load<Shader>로 읽는다 — Resources 안의 것은 전부 빌드에 들어간다.
  • 그 셰이더를 쓰는 재질(Material) 에셋을 만들어 씬이나 Resources에서 참조한다.
  • 프로젝트 설정의 Always Included Shaders 목록에 넣는다.
그래도 대비책은 둔다

기기가 그 셰이더를 못 돌릴 수도 있다(shader.isSupported가 거짓). 그때 효과가 통째로 사라지는 것보다 예전 방식(그냥 흐려짐)으로 물러나는 편이 낫다. 셰이더 파일에 Fallback을 적어두는 것도 같은 생각이다.

한 줄 — 이름으로만 부르는 셰이더는 빌드에서 빠질 수 있다. Resources·재질 참조로 "쓰인다"를 엔진에 알려라.
↑ 목차
11

분홍색의 의미 — 셰이더 디버깅

debugging
정의

유니티에서 물체가 새빨간 분홍(마젠타)으로 보이면 "이 셰이더를 쓸 수 없다"는 뜻이다 — 컴파일 실패, 기기 미지원, 혹은 빌드에서 빠짐. 일부러 눈에 띄는 색을 쓰는 것이다.

왜 미리 확인하기 어렵나

셰이더는 일반 코드처럼 한 번 컴파일하고 끝이 아니다. 엔진이 HLSL을 기기별 언어로 번역하고(04), 실제 GPU 드라이버가 마지막으로 다시 컴파일한다. 그래서 C# 코드는 터미널에서 컴파일 검사를 할 수 있어도, 셰이더는 엔진을 띄워봐야 오류가 보인다. 어떤 기기에서만 깨지는 경우도 있다.

실무 습관
  • 새 셰이더를 넣으면 "분홍인지부터 본다"를 확인 목록 맨 위에 둔다.
  • 셰이더를 못 쓰면 예전 방식으로 물러나는 코드를 같이 둔다(10).
  • 복잡한 효과는 한 단계씩 켠다 — 색 그대로 → 구멍만 → 경계 빛까지.
한 줄 — 분홍 = 셰이더를 못 씀. 셰이더는 엔진을 띄워봐야 오류가 보이므로, 확인 1순위로 둔다.
↑ 목차
12

모바일에서 조심할 것 — 정밀도·분기·overdraw

mobile
정밀도

모바일 GPU는 계산 정밀도를 낮춰(half, 16비트) 빠르게 돌리는 경우가 많다. 해시 노이즈처럼 큰 수를 곱했다가 소수부만 쓰는 계산은 정밀도가 낮으면 무늬가 줄무늬·덩어리로 깨진다 → 그런 계산은 float로 둔다.

분기

GPU는 이웃 픽셀 여럿을 한 묶음으로 같이 돌린다. 묶음 안에서 if가 갈리면 양쪽 길을 다 걷는다. step·lerp·saturate로 "계산은 다 하고 결과만 고르는" 식이 보통 더 싸다.

overdraw

반투명한 것이 여러 겹 겹치면 같은 픽셀을 여러 번 칠한다. 연기·불꽃·파티클이 화면을 덮으면 모바일이 가장 먼저 버거워하는 지점이다. 그래서 자주 나오는 연출(예: 판당 수백 번 나오는 처치 효과)은 작고 짧게 만든다.

한 줄 — 모바일에선 정밀도는 필요한 곳만 높이고, 분기 대신 수식, 반투명은 작고 짧게.
↑ 목차
13

셰이더가 못 고치는 것 — 대비는 그림의 몫

limits
겪은 일

몸이 녹는 셰이더 위에 재가 피어오르는 그림을 얹었는데 Play에서 "재가 안 보인다"가 나왔다. 재봤더니 재의 평균 밝기 0.50, 바닥 두 종류가 0.34와 0.61 — 재가 정확히 두 바닥 사이에 끼어 어느 맵에서도 묻혔다. 유일하게 튀는 색인 주황 불씨는 픽셀의 1~2%뿐이었다.

왜 셰이더로 못 고치나

색을 곱해 어둡게 하면 어두운 바닥에서 묻히고, 밝게 하면 밝은 바닥에서 묻힌다. 배경이 둘 이상이면 한 방향의 보정은 답이 없다. 어떤 배경에서든 읽히려면 그림 자체가 한 덩어리 안에 명암 폭(어두운 속 + 밝은 가장자리)과 배경에 없는 색(불씨)을 가져야 한다. 셰이더는 그림을 "어떻게 칠할지"를 바꾸지, 그림에 없는 대비를 만들어주진 못한다.

습관

효과 그림을 검수할 때 흰/검은 판이 아니라 실제 바닥 위에, 실제 크기로 얹어 본다. 밝기를 숫자로 재면 "내 눈이 이상한가?"를 바로 끝낼 수 있다.

한 줄 — 셰이더는 칠하는 법을 바꿀 뿐, 대비는 그림이 가져와야 한다. 검수는 실제 배경 위에서.
