00

TCP — 연결은 어떻게 맺고 유지되나

transport
정의

WebSocket은 TCP 위에서 돈다. TCP는 연결지향(connection-oriented)의 신뢰성 있는 양방향 바이트 스트림 — 순서 보장·재전송·중복 제거를 해준다. "연결"이라는 개념이 실제로 무엇인지 알아야 그 위의 WebSocket이 이해된다.

어떻게 맺나 — 3-way handshake

이 3번 왕복이 끝나면 양쪽이 "연결됨(ESTABLISHED)"으로 합의한다.

"서로 연결됐다"를 어떻게 아나 — 상태를 어디 저장?

연결은 추상적 개념이 아니라 양쪽 OS 커널이 들고 있는 상태다. 각 연결은 4-tuple로 유일하게 식별된다:

(출발지 IP, 출발지 port, 목적지 IP, 목적지 port)
예) (10.0.0.5, 51234, 10.0.0.9, 443)  ← 이 조합 하나 = 연결 하나

커널은 연결마다 상태 테이블에 이런 걸 보관한다:

  • 연결 상태(ESTABLISHED / TIME_WAIT 등)
  • 시퀀스/ACK 번호 (어디까지 보냈고 받았나)
  • 송신·수신 버퍼 (수십 KB) — 아직 안 읽힌/안 보낸 바이트
  • 윈도우 크기(흐름 제어) 등

이 테이블이 netstat/ss로 보이는 것이고, 애플리케이션엔 이 연결이 fd(file descriptor) 하나로 노출된다. 즉 "연결됨"을 아는 주체는 앱이 아니라 커널이고, 앱은 fd를 통해 그 위에 얹혀 있다.

데이터 주고받기 — "스트림"이라는 것

보낸 바이트마다 시퀀스 번호가 붙어 순서·재전송이 보장된다. 대신 TCP는 메시지 경계가 없다 — 그냥 바이트가 줄줄 흐르는 스트림이다. "여기까지가 한 메시지"를 TCP는 모른다. 그래서 상위 프로토콜(WebSocket 등)이 프레임으로 경계를 만든다(→ 카드 01).

끊긴 걸 어떻게 아나
  • 정상 종료: FIN/ACK 교환으로 서로 합의하고 닫음.
  • 비정상(크래시·전원): 상대는 모를 수 있다. 다음에 보낼 때 RST를 받거나, 오래 조용하면 keepalive/타임아웃으로 뒤늦게 감지. → 그래서 WebSocket이 앱 레벨 ping/pong으로 죽은 연결을 능동 감지한다(카드 01).
왜 중요 (다른 카드와 연결)
  • 연결마다 커널 자원(버퍼+fd)을 점유 → 연결 수 = 메모리. "연결은 비싼 자원"의 물리적 근거(카드 02·10).
  • 상태를 커널·프로세스가 들고 있음 → 프로세스/노드가 죽으면 그 연결도 사라진다(카드 09·13). 그래서 재연결+상태 복원 설계가 필요.
  • fd 총량은 OS 한도(ulimit -n)가 상한.
요약 — "연결"은 양쪽 커널이 4-tuple로 식별해 상태를 저장한 것. 3-way handshake로 맺고, 바이트 스트림(경계 없음)으로 주고받으며, 비정상 종료는 즉시 못 알 수 있어 상위에서 ping/pong으로 감지한다.
01

WebSocket — HTTP에서 어떻게 전환되고 무엇이 오가나

protocol
정의

HTTP Upgrade 핸드셰이크(응답 101)로 시작해, 그 뒤로는 하나의 TCP 연결 위에서 양방향으로 메시지 프레임을 주고받는 프로토콜. 요청-응답이 아니라 서버가 먼저 밀어줄(push) 수 있다는 게 핵심.

왜

REST 폴링은 클라가 주기적으로 물어봐야 하고(지연·낭비), 서버가 이벤트를 즉시 알려줄 수 없다. 실시간 시세·알림·진행 상태처럼 "바뀌는 순간 밀어줘야" 하는 데이터엔 지속 연결 + push가 맞다.

어떻게 전환되나 — 업그레이드 핸드셰이크

새 프로토콜로 새 연결을 여는 게 아니다. 이미 맺어진 TCP(카드 00) 위에서 평범한 HTTP 요청 하나로 시작해, 서버가 수락하면 그 같은 연결을 WebSocket 모드로 "승급(upgrade)"시킨다.

■ 클라 → 서버 : 평범한 HTTP GET 인데 특별한 헤더가 붙음
GET /path HTTP/1.1
Host: example.com
Upgrade: websocket            ← "이 연결을 ws로 승급하자"
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHN...  ← 랜덤 base64 (핸드셰이크 검증용)
Sec-WebSocket-Version: 13

■ 서버 → 클라 : 승급 수락
HTTP/1.1 101 Switching Protocols   ← 200이 아니라 101
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLM...    ← Key를 정해진 방식으로 해싱한 값

101 응답 이후로는 그 연결에서 HTTP가 끝나고, 양쪽이 WebSocket 프레임으로만 대화한다. Sec-WebSocket-Accept는 "나 진짜 ws 서버 맞다"를 증명하는 값(캐시/프록시가 우연히 통과시킨 게 아님을 보장).

데이터는 어떤 형태 — 프레임 구조

TCP는 경계 없는 바이트 스트림(카드 00)이라, WebSocket이 프레임으로 "여기까지가 한 조각"을 표시한다. 프레임 헤더의 핵심 필드:

  • FIN 비트: 이 프레임이 메시지의 마지막 조각인가 (큰 메시지는 여러 프레임으로 쪼갤 수 있음 = fragmentation)
  • opcode: 프레임 종류 — 0x1 text · 0x2 binary · 0x8 close · 0x9 ping · 0xA pong
  • payload 길이 + payload: 실제 데이터
  • mask: 클라→서버 프레임은 반드시 마스킹(XOR)됨 — 중간 프록시 캐시 오염 방지용 보안 장치. 서버→클라는 마스킹 안 함

메시지 vs 프레임: 논리적 "메시지" 하나 = 1개 이상의 프레임. 앱은 보통 메시지 단위로 다루고(text/binary), ping·pong·close는 제어용 프레임이라 데이터와 별개로 흐른다.

데이터 흐름 — 전이중(full-duplex)

요청-응답 짝이 없다. 양쪽이 언제든 독립적으로 프레임을 보낼 수 있다 — 서버가 클라 요청 없이 push하고, 클라도 아무 때나 보낸다. 한 연결이 읽기·쓰기 두 방향으로 동시에 흐른다(그래서 구현에서 읽기/쓰기를 분리 → 카드 11).

keepalive & close 코드
  • keepalive: 서버가 주기적으로 ping, 클라가 pong. 일정 시간 pong이 없으면 죽은 연결로 간주하고 끊는다(예: ping 25s / pong 대기 60s). TCP가 못 알려주는 "조용한 죽음"을 앱 레벨에서 잡는 장치(카드 00·13).
  • close 코드: 종료 이유를 숫자로 전달.
코드의미언제
1000정상 종료클라/서버가 얌전히 닫음
1001going away서버가 계획적으로 내려감(배포 등)
1006abnormalclose 프레임 없이 소켓이 죽음(크래시·네트워크)
1008policy violation정책 위반(예: 느린 소비자 강제 종료)
4000~4999앱 정의애플리케이션이 뜻을 정하는 사설 영역(예: 토큰 만료)
함정 (실측)

"ping/pong이 있으면 keepalive는 알아서 된다" — 클라 라이브러리에 따라 아니다. 많은 WS 클라(예: gorilla)의 기본 ping 핸들러는 pong만 보내고 read deadline을 안 늘린다. 그러면 "N초간 데이터 없으면 끊기"식 read deadline이 걸린 클라는, ping이 와도 데이터가 없으면 그 deadline에 스스로 끊는다. → ping 수신 시 read deadline을 직접 리셋해야 진짜 keepalive가 된다. (부하 테스트에서 "연결이 60초마다 통째로 끊기는" 미스터리의 흔한 원인 — 서버가 아니라 클라의 deadline 처리.)

요약 — WebSocket = 업그레이드 후 한 TCP 위 양방향 프레임. 값어치는 "서버 push". close 코드는 왜 끊겼는지를 담고, 4000번대는 앱이 의미를 정한다.
02

연결 하나 + 구독 멀티플렉싱

design
정의

여러 종류의 실시간 데이터를 받을 때, 종류마다 소켓을 새로 열지 않고 연결 하나 위에서 여러 채널(topic)을 구독하는 모델. 서버는 모든 채널을 같은 소켓으로 내려보내고, 클라는 메시지에 실린 채널 식별자로 구분한다.

왜

연결은 비싼 자원이다 — 핸드셰이크·인증 N회, keepalive·재연결 로직 N세트, 서버의 FD·메모리, 모바일 배터리. 종류마다 소켓을 열면 이 비용이 곱해진다. STOMP·MQTT·SignalR·성숙한 실시간 서버들이 전부 "연결 하나 + 구독 다중화"를 기본으로 한다.

어떻게

메시지마다 channel 필드가 있어 한 소켓에 여러 구독이 섞여도 구분된다. 새 데이터 종류는 "채널 하나 더 구독"으로 확장된다.

트레이드오프 — 언제 분리하나

물리적으로 소켓/게이트웨이를 분리하는 건 예외적 이유가 있을 때만: 다른 백엔드·인증 스코프, 장애·백프레셔 격리, 독립 스케일·수명. 격언: "분리는 나중에 더하기 쉽지만 합치기는 어렵다" → 기본은 하나로 시작.

03

봉투/내용물 분리

design
정의

봉투(envelope) = 라우팅·제어 메타데이터(채널, 구독/인증/에러 같은 제어 메시지). 내용물(payload) = 실제 도메인 데이터. 중간 계층(게이트웨이)은 봉투만 이해하고 내용물은 불투명 bytes로 통과시킨다.

우편 비유: 우체국은 겉면 주소(봉투)만 읽고 배달하지, 편지를 뜯지 않는다.

왜

중간 계층이 도메인 데이터를 파싱하면 데이터 스키마가 바뀔 때마다 중간 계층도 고쳐야 한다. 봉투만 알게 하면 내용물이 어떻게 바뀌든 중간 계층은 무수정 → 새 데이터 종류를 추가해도 게이트웨이 재배포가 필요 없다.

어떻게
ServerMessage {                 ← 봉투 (게이트웨이가 읽음)
  DataMessage {
    channel : "A"               ← 라우팅 키
    payload : <bytes>  ─────────┐ ← 게이트웨이는 안 뜯음
  }                             │
}                               └→ 도메인 객체 (양 끝단만 디코드)

제어 계층(구독 응답·에러·연결 통지)은 게이트웨이가 직접 생성/파싱하고, 데이터 계층은 생산자↔소비자 양 끝단만 해석한다.

흔한 오해

"내용물을 bytes로 감싸면 계약이 없는 것" — 아니다. 계약(스키마)은 여전히 중앙에 있고 양 끝단이 공유한다. 게이트웨이가 런타임에 안 열어볼 뿐. "모른다 = 파싱 안 한다"이지 "규격이 없다"가 아니다.

트레이드오프

내용물을 typed 필드로 두면(중간 계층이 타입을 앎) 타입 안전하지만 봉투가 도메인에 결합된다. bytes로 두면 완전 도메인-중립이지만 양 끝단이 디코드 한 겹을 더 한다(작은 CPU 비용). "중간 계층을 여러 소비자가 재사용"하려면 bytes 쪽이 유리.

04

스냅샷 vs 델타

design
정의

스냅샷 = 구독 직후 1회 내려주는 현재 전체 상태. 델타 = 그 뒤로 흐르는 변경분(증분 이벤트).

왜

변경 이벤트만 흘리면 지금 막 구독한 클라는 "아직 안 바뀐 것들"을 모른다(예: 정지 중인 항목). 그래서 처음 한 번 전체를 줘서 화면을 완성시키고, 이후엔 바뀐 것만 보내 대역폭을 아낀다.

어떻게
구독
 → 스냅샷: [전체 상태]          (한 번, is_snapshot = true)
 → 델타:   [바뀐 항목만]        (계속, is_snapshot = false)
 → 델타:   [바뀐 항목만]

같은 메시지 타입에 snapshot 플래그로 구분하는 게 흔하다. "무엇이 변경인가"의 판단은 데이터를 아는 생산자(도메인 서버)가 한다 — 중간 계층은 못 한다(내용물을 안 보니까).

요약 — 스냅샷 = "지금 전체 캡처", 델타 = 그 뒤 "여기 바뀜" 이벤트들. 델타는 이벤트 데이터로 봐도 좋지만, 스냅샷은 이벤트가 아니라 초기 상태 덤프다.
05

직렬화: protobuf vs JSON

encoding
정의

와이어로 나가는 건 결국 바이트다. 그 바이트를 사람이 읽는 텍스트(JSON)로 인코딩할지, 스키마 기반 바이너리(protobuf 등)로 인코딩할지의 선택. 논리 구조는 같고 인코딩만 다르다.

어떻게 — 같은 데이터, 다른 크기
항목 수protobufJSON배수
1개72 B172 B~2.4×
100개7,002 B14,321 B~2.0×

※ 특정 스키마의 실측 예시 — 절대값보다 "JSON이 대략 2배 뚱뚱"이라는 관계가 요점.

JSON: "lat","lon" 같은 키 이름을 매 항목마다 텍스트로 반복하고 숫자도 ASCII. 자기설명적이라 아무 언어나 파싱하지만 뚱뚱하다.
protobuf: 키 이름 대신 필드 번호만, 숫자는 바이너리. 스키마를 양 끝단이 공유하니 "번호 → 위치"로 바로 꽂는다. 작고 빠르지만 스키마에서 코드 생성이 필요.

트레이드오프
JSON스키마 바이너리(protobuf)
크기큼(키 반복)작음
접근성아무 언어·curl로 읽힘스키마/코드생성 필요
스키마 강제없음(오타 위험)타입·필드번호 강제
사람이 읽기가능바이너리

작은 메시지 · 고빈도 · 대량 연결이면 바이너리가 유리(2배 절감이 대역폭·비용에 곱해짐). 저빈도 · 디버깅 편의 · 다양한 소비자면 JSON이 편하다.

흔한 오해

"protobuf로 받아 JSON으로 본다"가 가능한가? — 와이어는 한 형식이다. protobuf 바이트를 JSON으로 그냥 읽을 순 없고, protobuf 디코더로 푼 다음 객체를 JSON으로 다룰 수는 있다(디코더는 필요). 단, 봉투는 bytes로 통과되므로 payload만 JSON으로 하는 혼용은 양 끝단이 약속하면 가능.

얇은 실시간 게이트웨이 패턴

architecture
정의

실시간 연결을 전담하는 얇은 중간 서비스. 딱 세 가지만 한다: ① 연결 유지(수많은 소켓의 수명 관리), ② 팬아웃(발행된 메시지를 구독자에게 뿌림), ③ 인증 위임(판정은 백엔드에, 집행만 게이트웨이). 도메인 로직·저장·비즈니스 규칙은 갖지 않는다.

왜

실시간 연결 관리(동시성·keepalive·백프레셔·팬아웃)는 일반 요청-응답 백엔드와 성격이 완전히 다르다. 이걸 도메인 서버에 섞으면 배포할 때마다 연결이 끊기고, 스케일 특성도 엉킨다. 연결 계층을 분리하면 도메인 서버는 자유롭게 배포·스케일하고 연결은 게이트웨이가 계속 유지한다.

어떻게 — 자작 vs 제품

성숙한 오픈소스 실시간 서버(예: Centrifugo류)는 recovery·presence·history 등 많은 기능을 준다. 하지만 필요한 게 "연결·팬아웃·인증"뿐이라면, 그 패턴만 얇게 직접 구현하는 편이 나을 수 있다. recovery/presence 같은 무거운 기능이 실제로 필요해지는 시점이 곧 제품 도입을 재검토할 신호.

요약 — 게이트웨이는 "연결 유지 · 팬아웃 · 인증 위임"만 하는 도메인-무지 파이프. 연결을 도메인 서버에서 떼어내는 게 목적이다.

인증 위임: connect proxy vs JWT 로컬검증

auth
정의 — 두 방식
  • JWT 로컬검증: 클라가 JWT를 들고 접속 → 게이트웨이가 설정된 키로 직접 검증. 사용자·만료·권한이 토큰 안에 들어 있어 백엔드 호출 없음.
  • connect proxy: 접속 시 게이트웨이가 백엔드로 요청 → 백엔드가 판정해 사용자·권한·만료를 응답. 게이트웨이는 그 결과로 집행만.
어떻게
트레이드오프 — 무엇이 선택을 가르나

토큰이 자체검증 가능한가 + 인가 재료가 토큰 안에 있는가가 관건.

  • 토큰이 불투명(introspect 필요)하거나, 권한(구독 가능한 채널 목록)이 DB 조회로만 나온다면 → 게이트웨이가 스스로 못 하니 connect proxy가 자연스럽다.
  • 토큰이 서명된 JWT이고 권한을 claim으로 담을 수 있으면 → 로컬검증으로 접속마다의 백엔드 호출을 아낀다.

proxy는 매 연결 백엔드 왕복이 있지만(연결은 드물게 생기므로 대개 수용 가능), 로컬검증은 빠른 대신 토큰에 권한을 실어야 하고 폐기(revoke)가 까다롭다.

핵심 — 인가 재료가 "토큰 안"이면 로컬검증, "백엔드/DB 안"이면 proxy. 게이트웨이는 어느 쪽이든 판정은 위임, 집행만 한다.

broadcast + local-deliver 팬아웃

scaling
정의

게이트웨이가 여러 파드(인스턴스)로 스케일아웃될 때, 발행된 메시지를 모든 파드에 broadcast(pub/sub 버스)하고, 각 파드는 자기 로컬 구독자에게만 deliver하는 방식.

왜

구독자가 어느 파드에 붙어 있는지 발행자는 모른다. 전 파드에 뿌리고 각자 자기 것만 걸러내면 어느 파드도 다른 파드의 구독 정보를 알 필요가 없다 → 스티키 세션 불필요, 무상태 스케일아웃.

어떻게

전달 경로가 "버스 수신 하나"뿐이라 세션당 정확히 1회(중복·유실 없음), 발행이 어느 파드에 떨어져도 결과가 같다.

트레이드오프

구현이 단순하고 상태 저장소가 필요 없다. 대신 발행이 모든 파드로 간다 — 구독자 없는 파드도 받아서 버린다. 파드 수가 수십~수백으로 커지면 이 broadcast 낭비가 커져 채널별 샤딩/구독 라우팅을 고민할 시점(작은 규모엔 과함).

부수 개념 — 느린 소비자(slow consumer)

한 클라의 수신이 느려 송신 버퍼가 차면, 그 하나 때문에 전체 팬아웃이 막힐 수 있다. 대응: 버퍼가 가득 차면 그 연결을 끊어버린다(정책 위반 close). 클라는 재연결로 복구.

상태는 어디에 — 파드 로컬 vs 공유 저장소

architecture
정의

연결(소켓)과 구독 정보를 어디에 저장하나. 이 패턴에선 전부 파드 로컬 메모리에 둔다. pub/sub 버스는 메시지 전달용일 뿐 상태 저장소가 아니다(PUBLISH/SUBSCRIBE만, SET/GET 안 함).

어떻게
정보저장 위치
소켓 연결 객체그 소켓을 받은 파드의 메모리
구독(채널→세션 매핑)각 파드의 인메모리 맵
메시지 라우팅pub/sub 버스(저장 아님, 전달만)
트레이드오프

장점: 상태 저장소 없이 단순, 로컬 맵이라 빠름, 무상태 스케일아웃. 비용: 파드가 죽으면 그 파드의 연결이 사라진다 → 클라가 재연결해 다른 파드에 붙고 스냅샷으로 상태 복원(그래서 재연결+스냅샷 설계가 안전망). 연결을 절대 잃으면 안 되면 외부 세션 저장소가 필요하지만 대개 과설계.

Go 동시성 & netpoller — 왜 수천 연결이 싼가

runtime
정의

연결마다 고루틴 2개(읽기·쓰기)를 붙여도, 대부분 park(잠듦) 상태라 OS 스레드를 잡지 않는다. 런타임의 netpoller(리눅스 epoll)가 I/O 대기 고루틴을 재우고, 데이터가 도착하면 깨운다.

어떻게
  • 연결 = TCP 소켓 1개(= fd 1개) + 고루틴 2개(reader/writer).
  • conn.Read()가 blocking처럼 보이지만, 데이터 없으면 런타임이 그 고루틴을 epoll에 등록하고 재운다(스레드 안 잡음). 도착 시 깨워 실행 큐에 올림.
  • OS 스레드(M)는 소수(≈코어 수), 고루틴(G)은 수천 → M:N 스케줄링.
핵심 관계 — 두 자원이 다른 축
자원무엇에 비례이유
CPU처리량(초당 프레임)park에서 깨어나 실제 write하는 횟수
메모리(RSS)연결 수연결마다 고루틴 스택 + 커널 소켓 버퍼

즉 연결을 늘려도 트래픽이 없으면 CPU는 거의 안 오른다(다 잠들어 있으니). fd 총량은 OS 한도(ulimit -n / LimitNOFILE)가 상한.

요약 — "고루틴 = 스레드"가 아니다. blocking 코드처럼 보여도 netpoller가 논블로킹으로 돌려서, 스레드 고갈 없이 수천 연결을 얹는다. CPU ∝ 처리량, 메모리 ∝ 연결 수.

단일 writer 원칙

concurrency
정의

한 소켓에 대한 쓰기는 오직 한 주체(writer 고루틴)만 한다. 보낼 것이 여러 곳(데이터 팬아웃·만료 통지·에러 응답)에서 생겨도, 전부 채널(큐)에 넣고 writer 하나가 꺼내 소켓에 쓴다.

왜

여러 고루틴이 같은 소켓에 동시에 쓰면 프레임이 섞이거나 레이스로 크래시한다(대부분의 소켓 write는 동시 호출 안전하지 않음). 쓰기 지점을 하나로 직렬화하면 이 문제가 원천 차단된다.

어떻게
데이터(팬아웃) ─┐
만료 통지     ─┼─▶  send 채널  ─▶  [writer 고루틴 하나]  ─▶  소켓
에러 응답     ─┘                     (쓰기는 여기서만)

reader는 읽기만, writer는 쓰기만. 종료 시 close 프레임조차 writer를 거치게 해서 "쓰기는 writer만" 불변식을 지킨다.

함정

이 send 채널을 close하면 안 된다 — 보내는 쪽이 여럿이라 닫힌 채널에 send하면 패닉한다. 종료는 별도 신호(done) 채널로 알리고, writer가 그걸 보고 정리한다. (동시성 버그는 부하 테스트에서야 드러나는 경우가 많다.)

만료/재인증 — 판정은 위임, 집행은 로컬

auth
정의

토큰 만료 시각은 백엔드가 정하고(판정), 게이트웨이는 세션마다 타이머를 걸어 그 시각에 끊는다(집행). 만료 전 새 토큰으로 in-band 재인증하면 타이머만 갱신하고 연결은 유지한다.

어떻게
연결 수립  → 만료시각 exp 수신 → 타이머 예약(exp 시점)
재인증     → 기존 타이머 취소 → 새 exp로 재예약 (연결 유지)
만료 도달  → 만료 통지 프레임 → 앱-정의 코드로 close
exp == 0   → 만료 없음 → 타이머 안 검
트레이드오프 / 주의
  • 만료 없는 토큰이면 재검증 타이머 자체가 없어, 백엔드가 잠깐 죽어도 기존 연결은 안 끊긴다(연결은 게이트웨이 소유). 백엔드 장애가 실시간 연결을 안 끊는 이점.
  • 반대로 즉시 폐기(revoke)가 어렵다 — 이미 연결된 세션은 만료 타이머 전까진 유효. 강제 폐기가 필요하면 별도 신호(관리 API로 끊기)가 필요.

graceful vs 장애 종료 & 재연결

ops
정의

연결이 끊기는 방식은 계획된 종료와 장애가 다르고, 클라가 받는 신호도 다르다. 재연결 로직은 이 모든 경우를 처리해야 한다.

어떻게 — 종료 방식별 신호
상황메커니즘클라가 받는 것
계획 종료(배포·스케일)SIGTERM → 서버가 close 프레임 전송 후 종료1001 going away
프로세스 크래시(OOM·panic·SIGKILL)즉사 → close 프레임 못 보냄1006 abnormal
노드/네트워크 단절소켓이 조용히 죽음, 신호 없음무신호 → ping/pong 타임아웃으로 뒤늦게 감지
설계 교훈

재연결을 close 코드로 분기하면 위험하다 — 1001만 처리하고 1006·무신호를 놓치면 진짜 장애 때 재연결이 안 된다. 안전한 규칙: "어떤 이유로든 소켓이 닫히면 무조건 재연결(백오프)". 재연결 후 스냅샷으로 상태를 복원한다.

테스트 팁

계획 종료(1001)는 인스턴스를 0으로 스케일해 재현. 진짜 장애(1006)는 프로세스를 강제 종료(SIGKILL)해 재현. graceful만 테스트하면 실제 장애에서의 폴백을 검증 못 한 것이다.

14

멀티 파드 스케일링 & 세션 분산

scaling
정의

지속 연결(WS)을 여러 파드로 스케일할 때 세션이 어떻게 분산되나. 핵심: 이미 맺어진 연결은 파드 간 이동하지 않는다(카드 08 팬아웃의 연장).

왜 기존 연결은 안 옮겨가나

WS 연결은 오래 사는 TCP 소켓이고, 그 소켓 상태는 받은 파드의 커널·메모리에 묶여 있다(카드 00·09). 파드를 하나 더 띄운다고 이미 열린 소켓이 이사 가지 않는다 — 마이그레이션 메커니즘 자체가 없다.

어떻게 — 스케일업 vs 처음부터 N개
스케일 1→2:
  Pod A [기존 1000개 그대로]  +  Pod B [0개]
  → 이후 "신규 연결만" LB로 A·B 분산
  → 초반 쏠림(A=1000+α, B=α) → 연결 churn(만료·재연결)으로 서서히 평준화

처음부터 2개:
  모든 연결이 신규 → 램프업하며 A·B로 갈림 → ~50/50 균등

즉 "파드 추가 = 즉시 반반"이 아니다. 기존은 고정, 신규만 분산이라 스케일업 직후엔 불균등하고, 시간이 지나며 재연결로 고르게 된다.

신규 연결 분산 — LB 알고리즘
정책동작WS 적합성
round-robin (기본)순번대로 배분, 기존 부하 무시새 파드가 늦게 참
least-connection연결 수 적은 파드로 몰아줌새 파드가 빨리 따라잡음

오래 사는 연결은 한번 붙으면 오래 남으므로, "지금 연결 수가 적은 곳"으로 보내는 least-conn이 균형에 유리하다.

least-conn의 실제 로직 — "전체 최소"가 아니라 P2C

"연결 적은 파드로"는 결과고, 실제 알고리즘은 Power of Two Choices (P2C)다(Envoy LEAST_REQUEST 등):

신규 연결마다:
  1. 전체 파드 중 무작위 2개를 뽑는다
  2. 그 둘의 active request(≈열린 연결) 수를 비교
  3. 더 적은 쪽으로 보낸다      // 전수 스캔 아님, 뽑는 개수는 보통 2

왜 전체 최소가 아니라 2개만? 전수 "지금 최소"를 항상 고르면 여러 LB가 동시에 같은 파드로 몰려(herd/dogpile) 오버슈트·진동한다. P2C는 O(1)이면서 최대 부하를 지수적으로 개선(Mitzenmacher)해 조율 없이 near-optimal. 그래서 확률적이라 완벽 균등은 아니고 "적은 쪽으로 강하게 쏠림". LB 인스턴스가 여러 개면 각자 부분 뷰로 P2C해서 실측이 77%(100% 아님)로 나온 이유가 이것.

오래 사는 WS는 연결 하나 = active request 하나(열린 동안 계속 카운트)라, "active request ≈ active connection"이 되어 연결 균형에 잘 맞는다.

실측 교훈 — 기본값부터 확인

"least-conn을 명시적으로 설정하라"가 항상 필요한 건 아니다. 인프라의 기본 LB를 먼저 확인하라. 실측: 어떤 서비스 메시(카드 15)는 최신 버전에서 기본 LB가 이미 least-request(P2C)였다 — 빈 파드로 신규 연결의 77%를 보냈다(명시 round-robin은 50%). 즉 명시 설정이 redundant였다. 교훈: 고도화를 코드/config로 추가하기 전에, 플랫폼이 이미 해주고 있는지 실측·확인한다. (least-conn / least-request는 보통 같은 것으로 매핑된다.)

흔한 오해

"파드를 추가하면 부하가 바로 반반 된다" — 아니다. 기존 연결은 원래 파드에 그대로 남고 신규만 분산된다. 라운드로빈이면 새 파드는 한참 놀 수 있다.

쏠려도 정확성은 안 깨진다 (핵심)

분산이 불균등해도 broadcast + local-deliver(카드 08) 덕에 메시지 전달은 정상이다: 발행 → 버스가 전 파드에 broadcast → 각 파드가 자기 로컬 구독자에게 push. Pod A가 900명, Pod B가 100명이어도 둘 다 받는다. 분산은 부하 균형 문제일 뿐 정확성과 무관.

리밸런싱

자동 리밸런싱은 없다. 고르게 하려면: (1) 기다림 — churn으로 자연 평준화(보통 충분), (2) 파드 드레인 — 그 연결들이 재연결하며 재분배(순간 재연결 폭풍), (3) least-conn LB로 신규를 적은 쪽에.

요약 — 지속 연결은 파드에 묶여 스케일업 시 기존은 고정, 신규만 분산. 처음부터 N개면 균등한 건 전부 신규라서. 불균등해도 broadcast 팬아웃이 정확성을 보장하고, 균형은 churn·least-conn·드레인으로 맞춘다.

서비스 메시 (Istio) — 앱 밖의 네트워킹 계층

infra
정의

서비스 메시(service mesh) = 서비스 간 네트워킹(라우팅·로드밸런싱·TLS·재시도·타임아웃·관측)을 앱 코드 밖 인프라 계층에서 대신 처리하는 것. Istio가 대표 구현이고, 내부적으로 Envoy 프록시를 쓴다.

왜

모든 서비스가 각자 재시도·타임아웃·mTLS·로드밸런싱을 코드로 짜면 중복·불일치·언어별 편차가 생긴다. 이걸 인프라로 빼면 앱은 비즈니스 로직만 남고, 네트워킹 정책은 한 곳에서 선언적으로 통제된다.

흔한 오해 — "이거 특정 클라우드 기능?"

아니다. Istio는 클라우드 무관 오픈소스(CNCF)다. 특정 매니지드 쿠버네티스(AWS EKS / Google GKE / Azure AKS)의 기능이 아니라, 아무 쿠버네티스 위에 직접 설치하는 별도 계층이다. "EKS에서만 봤다"면 그 클러스터에 팀이 Istio를 설치한 것일 뿐 — GKE·온프렘에서도 똑같이 쓴다. 계층을 나눠보면:

계층무엇예
매니지드 K8s클라우드가 운영해주는 쿠버네티스EKS(AWS) · GKE · AKS
서비스 메시K8s 위에 설치하는 네트워킹 계층Istio · Linkerd · Consul · (AWS App Mesh)
데이터플레인 프록시메시가 부리는 실제 프록시Envoy(Istio가 사용) — 이것도 별도 OSS

즉 EKS = 매니지드 쿠버네티스, Istio = 그 위에 얹은 메시(선택 설치), Envoy = Istio가 쓰는 프록시. AWS엔 자체 메시(App Mesh)도 있지만, 기능·클라우드 중립성 때문에 Istio를 택하는 팀이 많다.

어떻게 — 사이드카 프록시

각 서비스 파드 옆에 프록시(사이드카)를 주입해 그 서비스의 모든 트래픽을 가로챈다. 외부 트래픽은 전용 Ingress Gateway(역시 Envoy)가 받아 메시 안으로 라우팅한다. 중앙 컨트롤 플레인이 이 프록시들을 설정한다.

핵심 리소스(개념)
리소스역할
Ingress Gateway외부 트래픽 진입점 (어느 포트/프로토콜을 받나)
VirtualService라우팅 규칙 — 어느 호스트/경로 → 어느 서비스
DestinationRule서비스별 정책 — 로드밸런싱, 커넥션 풀, TLS
이 시스템과의 연결

WS 연결은 클라 → Ingress Gateway(Envoy) → 게이트웨이 파드로 흐르고, 그 파드 분산(카드 14)을 메시의 LB가 한다. LB 정책은 DestinationRule로 바꿀 수 있다. 단 실측 결과 이 메시는 기본 LB가 이미 least-request여서 명시 설정이 불필요했다(카드 14). "인프라가 이미 해주는지 먼저 확인"의 사례.

트레이드오프

장점: mTLS·트래픽 제어·재시도·관측을 앱 수정 없이 공짜로. 비용: 복잡도, 사이드카마다 프록시 리소스(메모리·지연 약간), 러닝커브. 작은 시스템엔 과할 수 있어 — 필요(다수 서비스 간 보안·트래픽 제어)가 생길 때 도입가치가 커진다.

요약 — 서비스 메시 = 앱 밖에서 서비스 간 네트워킹을 대신하는 계층(프록시 사이드카 + 컨트롤 플레인). 로드밸런싱·라우팅·TLS가 여기 살고, VirtualService(라우팅)·DestinationRule(정책)로 선언적으로 제어한다.

이중 쓰기 & 적응형 폴백

resilience
정의

새 경로(primary)로 이관하는 전환기에 기존 경로(fallback)에도 같이 쓰는 것이 이중 쓰기(dual-write). 기존 경로가 비싸면 그냥 끄고 싶지만, primary 장애 시 폴백이 필요하다 — 그래서 기존 경로를 "끄기"가 아니라 "줄이되 살려두기"로 두고, 장애 시 자동으로 키우는 게 적응형 폴백이다.

왜 "에러시에만 폴백"이 위험한가 — cold-start gap

"평소엔 primary만, 장애 나면 그때 fallback 쓰기 시작"은 구멍이 있다: 장애 순간 fallback엔 최근 데이터가 없다(안 쓰고 있었으니). 폴백한 소비자는 장애 초기에 stale/빈 데이터를 본다. → 폴백이 의미 있으려면 fallback이 어느 정도 최신을 유지(warm standby)해야 한다.

어떻게 — write rate = f(primary 건강)
primary 정상 → fallback throttle (예: 5s마다 최신값 1회, 저비용·warm)
primary 장애 → fallback 100% (실시간, 서킷브레이커가 boost)
primary 복구 → fallback 다시 throttle down
방식fallback 비용폴백 품질
풀 이중화100%완벽(실시간)
throttle+boost (권장)평소↓, 장애시만↑warm(수초 stale)→장애시 실시간
error-only거의 0장애 초기 cold(구멍)

핵심 절감 원리: 99%의 정상 시간엔 throttle(coalesce — 엔티티별 최신값만), 드문 장애 때만 풀 → 기대비용 최소, 폴백은 매끄럽게.

⚠️ 전제 — throttle은 데이터 종류를 가린다

위 throttle/coalesce는 아무 데이터에나 쓰면 안 된다. 데이터가 두 종류로 갈리고, 전략도 갈린다:

연속 상태값 (예: 위치)이산 이벤트/전이 (예: 상태 변경)
의미최신만 의미 있음각 이벤트가 discrete — 하나가 곧 사건
coalesce/throttle✅ 안전(중간값 버려도 됨)❌ 금지(A→B→C에서 B 유실=버그)
실패 시fire-and-forget OK — 다음 값이 덮어써 자가치유유실 영구 — at-least-once(재시도/outbox) 필요
순서무관(최신이 진실)중요(전이 순서가 의미)

우아한 지점 — 둘이 안 부딪힌다: 비싼 건 고빈도 연속값(위치)인데 이건 손실 OK. 못 버리는 건 이산 이벤트인데 보통 저빈도라 전부 써도 싸다. → "비싸서 줄일 것"과 "못 줄일 것"이 서로 다른 데이터라, 데이터 종류로 경로를 나누면 비용 절감과 무손실이 동시에 성립한다.

연속값(고빈도·손실OK):   실시간 push + fallback throttle+boost + fire-and-forget
이산이벤트(저빈도·무손실): 실시간 push + fallback 전부(throttle 없음) + at-least-once(재시도/outbox) + 순서보장
                          ↑ 저빈도라 다 써도 비용 부담 없음
엣지: 이산이벤트가 고빈도가 되면 → throttle 아니라 durable queue(Kafka/outbox)
두 실패 도메인 — boost는 systemic에만
장애 유형감지 주체대응
생산자→primary 끊김 (systemic)생산자가 write 실패로 감지서킷브레이커 → fallback boost
primary→특정 소비자 끊김 (개별)생산자는 모름그 소비자가 스스로 fallback 읽기(warm 데이터)

즉 boost는 "전체 장애"에만 발동하고, 개별 소비자 문제는 warm throttle + 재연결이 흡수한다. 생산자는 자기가 못 보는 소비자 상태를 boost 근거로 삼을 수 없다.

주의

서킷브레이커의 감지 지연(연속 실패 N회)만큼은 아직 throttle 상태 → 그 창에서 소비자는 warm(수초+감지시간) stale을 본다. 감지를 빠르게. 또한 소비자에 폴백 스위칭 로직이 있어야 완성된다(primary 끊기면 fallback 읽기 → 복구되면 복귀).

요약 — 이관 중 이중 쓰기에서 비싼 fallback을 "끄기"가 아니라 "정상=throttle(warm) / 장애=서킷브레이커가 100% boost"로 두면 비용↓·폴백은 매끄럽다. "에러시에만"은 cold-start 구멍이 있다. 완전 이관되면 fallback 제거(또는 DR용으로 throttle 유지).
